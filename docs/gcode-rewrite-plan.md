# План: переработка генерации G-code (`js/export/gcode.js`)

Статус: этап 1 выполнен, этапы 2–4 выполнены (ветка `refactor/gcode-pipeline`, см. «Статус реализации»). Эталонные УП: `docs/reference/*.nc`.

## Текущее состояние

- Один `.tap` на пару (сторона, инструмент): `<order>-{лиц|тыл} ф<d>х<len>.tap`.
- Инструменты `TOOLS`: 4x17, 4x22, 8x32, 8x42; обороты, подача, глубина за проход, шаг — заглушки.
- `pickTool`: глубина ≤ 15 мм → 4x17; иначе 8x32 (плита 30 мм) или 8x42 (≥ 40 мм).
- Вывод только G1 (нет G2/G3), ClipperLib offset (масштаб 1000×, 96 сегментов на окружность).
- Зигзагообразный вход (`buildRampedPass`), Z=0 на поверхности стола, safeZ = толщина + 10 (будет фиксированные 50).
- Зеркалирование X для нижней стороны, ориентация vertical = поворот на 90° CCW.
- millType: outside / inside / contour / pocket (концентрические кольца).
- `layers.js` → `machining` (side/depth/depthAnchor/millType) — заглушки.

### Проблемы

- Режимы резания — заглушки.
- ClipperLib не проверен в браузере на реальных данных.
- Тесты удалены 2026-10-14.
- Нет G2/G3, нет перемычек (tabs) / «шкурки» для сквозных резов.
- Лишние подъёмы, Z-ноль на столе, а не на плите.

## Целевая архитектура

### 1. Конвейер

`entries → operations → toolpaths → ordering → post-processor → text`

- **operations** — из machining-профиля (что и чем обрабатывать).
- **toolpaths** — только геометрия с уровнями Z, без диалекта.
- **post-processor** — единственная часть, знающая диалект: header/footer, формат чисел, смена инструмента, окончания строк. Новый контроллер = новый post.

### 2. Machining-профиль как данные

- Инструменты, подачи/обороты по материалу и толщине, глубина за проход, шаг, правила выбора инструмента.
- `layers.js` оставляет только стиль и семантический тип (сквозной рез, карман, гравировка).

### 3. Качество траекторий

- Настоящие G2/G3 (**приоритет**, станок поддерживает) (arc-fit результата Clipper или аналитический offset окружностей/дуг).
- Карманы через Clipper PolyTree (острова).
- Чистовой проход по стенкам; доработка остатка (rest machining: 4 мм после 8 мм).
- Спиральный вход для отверстий; рампа для контуров; lead-in/out.
- Climb / conventional на операцию.

### 4. Порядок обработки

- Сначала карманы и отверстия, внешний контур последним.
- Nearest-neighbor; глубина «до конца» по контуру, без лишних подъёмов.

### 5. Превью и проверки

- Оверлей траекторий, время обработки, проверка границ.
- Предупреждения: Z ниже стола, карман уже инструмента, самопересечения.

### 6. Опционально

- Z-ноль на поверхности плиты.

## Порядок работ (кратко; подробно — в разделе «Реализация»)

1. Конвейер + профиль + post-processor; вывод по формату эталонных `.nc` (NCStudio).
2. G2/G3, порядок обхода, вход/выход.
3. Карманы с островами, чистовой проход.
4. Превью и проверки.

## Ответы владельца (2026-11-08)

- ПО станка: **NCStudio 5.5.60**. Эталонные `.nc` — рабочие, из реального производства (не «идеальные»).
- **Перемычки не нужны**: столешница режется из мебельного щита в размер, держится на вакууме.
- **Приоритет — простота**; качество/скорость — позже. Текущие режимы резания работают терпимо.
- Реальные условия: тупые фрезы, плохой материал, слабый вакуум, неточный станок → не усложнять, оставить настройки легко правимыми.

## Что видно в эталонных `.nc` (DSK1141, плита 40 мм)

Формат (держать побайтно близким к эталону):
- Шапка: `T1M6`, `G17`, `G0Z50.000`, `G0X0.000Y0.000S<об>M3`; конец: `G0Z50.000`, `G0X0.000Y0.000`, `G0Z50.000`, `G0X0.000Y0.000`, `M30`. Файл заканчивается пустой строкой.
- Безопасная высота **Z50 — фиксированная** (владелец подтвердил), а не `thickness + 10`: `safeZ` в профиле = 50. Подача `F` задаётся отдельной строкой `G1F4000.0` / в первом `G1Z..F..`.
- Перевод строки в эталонах **CRLF** (и текущий код тоже пишет CRLF) — сохранить.
- Координаты с 3 знаками; **модальный вывод** — повторяющиеся X/Y/Z и `G1` опускаются (`G1X..`, потом просто `X..Y..`).
- Z-ноль на поверхности стола; верх плиты = Z40.
- **G2/G3 используются активно** (дуги в I/J, относительные), станок их поддерживает. Окружности — 4 дуги G3 по 90°; контуры — смесь G1 и G2/G3.

Параметры по инструментам:
| Файл | Фреза | Обороты | Подача | Z-диапазон | Примечание |
|---|---|---|---|---|---|
| 4_17 | ф4х17 | S24000 | гравировка F3000, рез F6000 | 25…50, 34.5…50 | F3000 — **гравировка** (медленнее, весь контур на 3000, глубина ≈0.5 мм в `a`); F6000 — обычный рез |
| 8_42 | ф8х42 | S18000 | F4000 | **0…50** | сквозной рез **до Z0**, без «шкурки» |

Приёмы, которые уже используются в эталоне:
- Спиральный (винтовой) вход для отверстий: G1-спираль вниз с шагом ≈1–1.5 мм на виток, затем чистовой круг G3.
- Зигзаг-рампа для контуров/карманов: движение туда-обратно с постепенным снижением Z (шаг порядка 2.7 мм на проход для ф8).
- Отверстия делаются концентрическими кольцами G3 (расширяющимися) до нужного диаметра.
- Карманы — вложенные контуры внутрь (offset внутрь с шагом ≈3 мм для ф4).
- Мелкие отверстия — спираль + финишный круг, пары проходов (грубо/чисто).

Выводы для плана:
- Цель этапа 1 — **совпасть с форматом эталона**: шапка (добавить `G17`), футер (`G0X0.000Y0.000`, а не `G0X0Y0`), модальный вывод, CRLF, 3 знака.
- G2/G3 — не «опционально»: станок их ест, эталоны ими пользуются. Переносим в этап 2, раньше «карманов с островами».
- Перемычки/«шкурку» из плана **убрать**.
- Сквозной рез до Z0 — норма (проверить, что пока совпадает с `resolveDepth`).
- Приоритет «простота»: профиль режимов — один понятный файл/объект с текущими рабочими значениями (из эталонов), без сложной логики rest machining на первом этапе.

- **Этап 2 — сделано**: окружности аналитически (G2/G3 по 90°, винтовой вход, шаг 3 мм/оборот); круглые карманы режутся от центра наружу кольцами без подъёма; arc-fit для остальных контуров (дуга по методу наименьших квадратов через концы участка; допуск вершин 0.02 мм, выпуклость над звеном 0.03 мм — исходные кривые тесселированы, их хорды сами лежат внутри кривой на сотые доли мм; дуга ≤ 90°); сквозные резы — последними.
- **Этап 2 — доделано**: направление обхода (climb) для всех контуров — внутренние против часовой (G3), внешние по часовой (G2); порядок обработки: сквозные последними, внутри класса — ближайший сосед по целым контурам (кольца одного кармана остаются вместе).

Превью строится из тех же программ, что и экспорт (`ExportGCode.buildPrograms`).

## Реализация (подробно)

Работа ведётся в ветке **`refactor/gcode-pipeline`** (от `main`). В `main` до готовности этапа попадает только документация. После каждого этапа — PR в `main`, пользователь проверяет УП на станке (холостой прогон / NCStudio-симуляция) до слияния.

### Базовые правила

- Публичный API `ExportGCode` не меняется: `buildFiles(entries, p, orderNumber)`, `downloadAs(...)`, `downloadAll`, `TOOLS`, `pickTool`, `resolveDepth`. Единственный вызов — `js/ui/app-render.js` → `ExportGCode.downloadAs(...)`, его не трогаем.
- Vanilla JS, без сборщика: новые файлы подключаются обычными `<script defer>` в `index.html` (в `geometry-editor/index.html` gcode не подключён) **и добавляются в `PRECACHE` в `sw.js`**; при удалении/переименовании файлов — поднять `CACHE_VERSION` (`v2` → `v3`).
- Стиль кода: `const X = (() => {...})()`, `Geo.*` для геометрии, комментарии «почему», как в текущем `gcode.js`.
- Тесты в репозиторий не добавляем (решение 2026-10-14). Проверка — одноразовым скриптом вне репозитория (см. «Контроль регрессий»).

### Структура модулей (целевая)

| Файл | Глобальное имя | Что внутри | Знает про диалект? |
|---|---|---|---|
| `js/export/gcode-profile.js` | `GCodeProfile` | инструменты (диаметр/длина/обороты/подача/проход/шаг), правила выбора фрезы, `resolveDepth`, режимы по типу операции | нет |
| `js/export/gcode-toolpath.js` | `GCodeToolpath` | ориентация/зеркало, Clipper-offset, заготовки траекторий, рампа/спираль, **результат — массив абстрактных `Move`** | нет |
| `js/export/gcode-post.js` | `GCodePost` | `Move[]` → текст: шапка/футер, `F`, модальный вывод, формат чисел, CRLF | да (NCStudio) |
| `js/export/gcode.js` | `ExportGCode` | фасад: группировка записей по (сторона, фреза), вызов профиля/траекторий/поста, имена файлов, скачивание | нет |

Порядок `<script>`: `gcode-profile.js`, `gcode-toolpath.js`, `gcode-post.js`, затем `gcode.js` (после `png.js`, как сейчас).

### Модель данных

- **Operation** (из профиля): `{ layerId, side, tool, millType, startZ, targetZ, feed, plungeFeed, direction }` — «что и чем обрабатывать».
- **Move** (абстрактное движение, абсолютные координаты станка, мм):
  - `{ t: 'rapid', x?, y?, z? }` → G0
  - `{ t: 'line',  x?, y?, z?, f? }` → G1
  - `{ t: 'arc', cw: bool, x, y, i, j, z?, f? }` → G2/G3 (I/J — смещение центра от начала дуги, как в эталоне)
  - В этапе 1 дуг нет — только `rapid`/`line`; тип `arc` и поддержка в посте закладываются сразу, чтобы этап 2 не менял контракт.
- **Toolpath**: `{ moves: Move[], entry: {x,y} }` — готовая последовательность одного контура на всю глубину; пост-процессор знает только `Move[]`.

### Этап 1 — безопасная перестройка (формат эталона)

Каждый шаг — отдельный коммит; после шагов 1–5 вывод **байт-в-байт** равен старому.

0. **Снимок «до»**: одноразовый node-скрипт (в scratchpad, не в репо) загружает `vendor/decimal`, `vendor/clipper`, `js/core/*.js`, `js/export/gcode.js` в `vm`, прогоняет набор фикстур (простая столешница, отверстия, карманы, нижняя сторона, вертикальная ориентация, плиты 30 и 40 мм, глубокие/мелкие слои) и сохраняет `.tap`-тексты как эталон «до».
1. **Профиль**: перенос `TOOLS`, `pickTool`, `SHALLOW_DEPTH_LIMIT`, `resolveDepth` в `GCodeProfile` без изменений логики. `ExportGCode` реэкспортирует их.
2. **Пост**: перенос `fmt`, `moveLine` (модальное состояние), шапки/футера, CRLF в `GCodePost`. Вход — `Move[]`. `buildRampedPass`/`emitToolpath` пока формируют `Move[]` вместо строк.
3. **Траектории**: перенос `toMachinePolyline`, `ORIENTATIONS`, `clipperOffset`, `ringArea`, `buildToolpaths`, рампы в `GCodeToolpath`; на выходе `Move[]`.
4. **Фасад**: `gcode.js` оставляет только `buildFiles`/имена/скачивание; удалить мёртвый код.
5. **Подключение**: `index.html`, `sw.js` (PRECACHE + `CACHE_VERSION`), проверка в Chromium (playwright) загрузкой `file://index.html`: экспорт из UI без ошибок в консоли, **заодно закрывает пункт «ClipperLib не проверен в браузере»**.
6. **Приведение к эталону** (намеренное изменение вывода, отдельным коммитом, diff «до/после» показать владельцу):
   - добавить `G17` после `T1M6`;
   - финальный `G0X0Y0` → `G0X0.000Y0.000`;
   - подача — отдельной строкой `G1F<feed>` / в первом `G1Z..F..` как в эталоне;
   - `safeZ` = 50 фиксированно (профиль); подача выбирается **по типу операции**: гравировка — 3000, рез — 6000 (ф4), ф8 — 4000; врезание на той же подаче, что и операция (как в эталоне). Тип «гравировка» — семантический тип слоя (см. «Machining-профиль»), не порог глубины;
   - сверить рампу с эталоном (в `8x42` рампа стартует с Z50, шаг по Z на проход не совпадает с `depthPerPass=10`): воспроизвести или осознанно оставить как есть.

### Этап 2 — G2/G3 и порядок обхода

- **Окружности аналитически**: запись из двух вершин с `bulge: 1` (отверстие) не идёт через Clipper; смещённая окружность — это окружность радиуса `r ± R`, пишется четырьмя дугами по 90° (как в эталоне). Спираль-вход для отверстий — по эталону (шаг ≈1–1.5 мм на виток), затем чистовой круг дугами.
- **Произвольные контуры**: оставляем Clipper (ломать устоявшийся offset снова не будем), поверх — **arc-fit** результата: жадный проход по точкам, участок заменяется дугой, если все точки лежат на окружности с допуском ~0.003 мм (плотность тесселяции 96 сегментов/круг даёт ошибку ≈0.001 мм, запас есть), минимум 3 сегмента, одно направление обхода. Остальное — `line`.
- Направление: `direction: 'climb'` по умолчанию, обход кольца нормализуется по типу операции (отверстие — G3, внешний контур — G2, как в эталоне); настраивается в профиле.
- **Порядок**: мелкие отверстия и карманы → внешний контур последним; внутри — ближайший сосед; Z-проходы одного контура подряд без лишних подъёмов.
- Карманы: кольца идут **изнутри наружу** и соединяются короткими `G1` без подъёма (как в эталоне), а не отдельными контурами с подъёмом на каждом кольце.

### Этап 3 — карманы с островами, чистовой проход

- Offset через `PolyTree` (острова), чистовой проход по стенкам с небольшим припуском, при необходимости rest machining ф4 после ф8. Только если упрёмся в качество (приоритет — простота).

### Этап 4 — превью и проверки

- Оверлей траекторий поверх чертежа (на основе `Move[]`), время обработки, проверка выхода за заготовку, предупреждения (Z ниже стола, карман уже фрезы, самопересечение).

### Контроль регрессий (без тестов в репо)

- Одноразовый скрипт сравнения «до/после» на фикстурах (шаги 1–5 — идентично; шаг 6 и этапы 2+ — читаемый diff).
- Дополнительно: прогон эталонных `docs/reference/*.nc` через простой парсер (подсчёт G0/G1/G2/G3, мин./макс. Z, границы XY) и сравнение со сгенерированным для той же столешницы DSK1141, если для неё есть чертёж.
- Перед боевым запуском: холостой прогон / симуляция в NCStudio, первый рез — на обрезке.

### Риски

- Clipper в браузере ещё не проверялся на реальных данных — шаг 5 этапа 1.
- Arc-fit может дать дуги с заметной ошибкой на слабо искривлённых участках → допуск вынести в профиль, при сомнении оставлять `line`.
- Кэш service worker: без поднятия `CACHE_VERSION` новые файлы могут не подхватиться офлайн.

## Решено (2026-11-08)

- Режимы резания зависят от диаметра, **не от длины** фрезы: ф4 (17/22) — как в эталоне 4x17, ф8 (32/42) — как в эталоне 8x42.
- Один файл на фрезу (как сейчас): смена инструмента ручная, `T1M6` в шапке.
